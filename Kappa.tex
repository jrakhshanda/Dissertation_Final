Title --- Representing Architectural Evidence in Software Systems: A Graph Learning Approach
% _________ Abstract __________
\begin{abstract}
Software architecture documentation is often missing, incomplete, or outdated, making it unclear which source files implement which architectural modules. Software architecture recovery infers a modular decomposition from the implementation, while code-to-architecture mapping assigns files to known modules using a partial mapping. Both tasks can use dependencies, folder structure, and source code, but existing methods often rely on individual sources or predefined combinations. It remains unclear what each source contributes and when propagating information between connected files helps rather than mixes evidence from different modules.

The research uses open-source Java, C, and C++ systems with published reference decompositions. Recovery studies examine learning objectives, graph construction, and information sources, while mapping studies investigate representations, graph-based propagation, and iterative self-training.

For architecture recovery, learned representations achieve agreement with reference architectures comparable to or better than the evaluated baselines. In the evaluated configurations, reconstruction generally outperforms contrastive learning, while random walks and diffusion capture structural information beyond direct dependencies. However, combining structural, lexical, and folder information can improve agreement with reference architectures while producing modules with weaker dependency cohesion than those obtained from dependency-based random-walk embeddings.

For code-to-architecture mapping, neural classifiers outperform a Naive Bayes baseline. A graph attention network outperforms a graph-free classifier on most systems, although gains vary by system and configuration. Folder information produces the largest and most consistent improvements, but higher accuracy can coincide with misclassifications of files that a simple directory rule assigns correctly. Representations that encode dependencies generally outperform lexical ones, and dependency-guided fine-tuning improves contextual representations. 

However, strong graph-model performance does not by itself demonstrate a benefit from additional message passing. Controlled experiments show that propagating dependency information can reduce performance for some predictors compared with matched models without cross-file messages. Changes to graph construction, propagation methods, or learning settings can reduce these losses or lead to improvements.

Together, these findings show that the usefulness of architectural information depends not only on what is available, but also on how it is represented, combined, and used.

\end{abstract}

\chapter{Introduction \label{ch:introduction}}
\chaptertoc

Software architecture provides an abstraction of a software system in terms of its principal elements, their responsibilities, and the relations among them~\cite{clements2003}. This abstraction supports reasoning about the system without requiring developers to inspect every implementation detail. However, the connection between the intended architecture and the source code is often incomplete or outdated~\cite{ali2018architecture,de2012controlling}. Recovering this connection relies on evidence from the implementation, which is distributed across multiple artifacts and their relations~\cite{negar,nsga3}. Prior work either uses such evidence in isolation or combines multiple sources to support architectural analysis~\cite{sarif,zbr,negar}. This thesis investigates how graph-based representation learning can use static implementation artifacts to support architectural analysis.

\section{Motivation}
\label{sec:intro-motivation}

Software architecture is often reflected in the implemented system as a modular decomposition: a partition of files into modules that group related functionality~\cite{parnas1972}. Such decompositions matter for program understanding, maintenance, and refactoring~\cite{clements2003}. As a system evolves, developers introduce dependencies that were not anticipated in the original design, refactor code across module boundaries, and add functionality that fits no existing module. Documentation is often not maintained in step with these changes. The resulting gap between the intended design and the implementation is described using two related terms: \emph{architectural drift}, where the implementation grows away from the intended design without directly violating it, and \emph{architectural erosion}, where the implementation directly violates the intended design~\cite{de2012controlling}.

Architectural drift and erosion can contribute to \emph{technical debt} by making later maintenance and change more costly~\cite{kruchten2012technicaldebt}. This concern may become more relevant as large language models (LLMs) are increasingly used to assist software development. A multivocal literature review reports that LLM-assisted development can amplify existing forms of technical debt, including design debt~\cite{ehsani2025fastercode}. An empirical study of AI-assisted development also reports short-term gains in development velocity alongside persistent increases in code complexity~\cite{he2026speed}. These findings provide additional motivation to assess architectural consistency, since changes that satisfy individual tasks may still conflict with the intended organization of responsibilities and dependencies across the system.

Two related activities address the gap between the intended architecture and its implementation. Software architecture recovery (SAR) is used when no sufficiently reliable architectural decomposition is available. It infers such a decomposition by grouping source-code files into architectural modules using evidence from the implementation. Performing recovery manually requires substantial knowledge of both the system and its domain, and becomes difficult as the number of files grows~\cite{garcia2013}.

Code-to-architecture (C2A) mapping is used when the architectural modules are known, but the assignments of source-code files to those modules are absent, incomplete, or outdated. It assigns files to these predefined modules~\cite{tzerpos1997orphan,christl2007automated}. The resulting mapping supports techniques such as reflexion modeling, which compare implemented dependencies with intended architectural relations~\cite{reflexion1}. Maintaining the mapping manually is costly because file assignments must be reconsidered as the implementation and architectural responsibilities evolve~\cite{ali2018architecture}.

Although the two activities differ in the architectural information available at the outset, both use implementation evidence to assign files to architectural modules. Dependencies, project organization, and source-code content offer potentially complementary evidence, motivating an investigation into how these signals can support recovery and mapping.

\section{Problem Statement}
\label{sec:intro-problem}

Both tasks assign source-code files to architectural modules, and a single implementation property does not determine a file's architectural role. Instead, evidence of module membership is distributed across several signals. Static dependencies describe how files call, import, inherit from, or otherwise use one another. Files that implement related responsibilities may be directly connected or occupy nearby regions of the dependency graph, making dependency structure a potential source of architectural information~\cite{negar}. Dependency types can also describe different forms of interaction and may not contribute equally to architectural similarity~\cite{edge_weights}.

Project organization, represented here by the folder hierarchy, provides a second signal. Folder hierarchies record how developers organize implementation artifacts and are commonly consulted when producing reference decompositions~\cite{garcia2013}. However, folders are implementation-level containers rather than architectural modules. A module can span several folders, and a folder can contain files belonging to several architectural concerns. Folder location, therefore, carries useful but imperfect evidence.

Source-code content provides a third signal. File names, identifiers, and comments encode domain-specific knowledge about the concepts and responsibilities a file implements~\cite{sarif}. Files from the same module may therefore share terminology, and lexical content has been used to group files by semantic similarity in prior recovery work~\cite{arc,zbr}. However, vocabulary can also recur across modules, particularly in shared abstractions and utility code. Lexical similarity is therefore informative, but may be insufficient on its own.
These signals may provide complementary evidence, but their combination is not straightforward. A modular decomposition is expected to have high \emph{cohesion} within modules and low \emph{coupling} between them~\cite{bunch_sahc_nahc}, and each signal is only an indirect indicator of these properties. A dependency can connect files within the same module or cross a module boundary. A folder can approximate a module or reflect only organizational conventions. Similar identifiers can indicate shared responsibility or merely the use of a common domain vocabulary. The strength of each signal can therefore vary across systems and modules.

Prior approaches, reviewed in Section~\ref{sec:bg_prior}, include dependency-based approaches~\cite{bunch_sahc_nahc,acdc,wca,negar}, lexical approaches~\cite{zbr,arc}, and lexical models that encode dependencies as tokens~\cite{olsson2022automatically}. Approaches that rely on a single source can leave potentially complementary evidence unused. To incorporate such evidence, several approaches combine multiple signals through predefined similarity functions or weighting schemes~\cite{sarif,sade,sc_misra}.

Graph neural networks (GNNs) offer a way to learn from these signals jointly by mapping the dependency graph, along with the attributes attached to its nodes and edges, into a common vector space. This does not by itself determine what is learned. The result depends on how files are represented, how the graph is constructed, how information is shared between connected files, and what objective drives learning. When several of these change at once, a difference in performance cannot be attributed to any one signal. Two further questions remain open: whether an added signal contributes beyond what the representation already encodes, and whether sharing information between connected files helps or instead mixes evidence from different modules when their relations cross architectural boundaries~\cite{gnn_homophily}.

The problem addressed by this research is therefore not only how to combine implementation signals. It is to examine what architectural information each signal carries, how that information should be represented, how the signals interact when combined, and under which structural conditions propagation along the graph is beneficial. Answering this requires varying input representation, graph construction, relation modeling, and message passing separately, and examining how they interact.

\section{Research Aim and Scope}
\label{sec:aim_scope}

This thesis investigates how graph-based representation learning can support software architecture recovery and code-to-architecture mapping. It examines the architectural information available in static implementation signals and how their usefulness changes with the input representation, graph structure, and message-passing mechanism.

This thesis aims to determine how graph-based representation learning can be designed for recovery and mapping, what architectural information the underlying implementation signals carry, and how the contribution of file representations changes when folder organization and member-level detail are added to the graph and dependency neighbors are made available through message passing. Both tasks are studied under a common perspective. Files and other implementation artifacts are represented as nodes, and their relations as edges; artifact-level information is provided as node attributes, and a graph representation-learning encoder produces file representations used to assign files to architectural modules.

The investigation starts with file-level dependency graphs in which the signals are supplied as node attributes, examines the signals individually, and then adds two further node types, with member nodes used only for mapping. A folder node represents a directory and is connected to its parent folder and to the files it contains. A member node aggregates all program elements of a single source file, such as its methods and fields, and is connected to that file. Adding these nodes only after the signals have been examined individually makes it possible to separate the effect of the initial file representation from the effects of graph structure and of the way information is shared between connected files. The aim is not to identify one graph model or representation that is uniformly preferable, but to examine under which conditions different signals and learning mechanisms are useful.

The thesis assigns source-code files to architectural modules and evaluates the assignments against a published reference decomposition. The file is the unit of analysis throughout. Member-level information may serve as evidence, but assignments are not made at the class, method, or subsystem level. The thesis spans unsupervised recovery and supervised mapping with limited labeled data and considers static implementation artifacts: dependencies, folder organization, and source code content. Other sources of evidence, such as commit co-change history and dynamic dependencies observed at runtime, are not studied. Chapter~\ref{ch:research_objective} states the formal problem and the objectives.

\section{Thesis Contributions}
\label{sec:intro-contributions}

The thesis makes four contributions: three research contributions, each corresponding to one research objective described in Chapter~\ref{ch:research_objective}, and one methodological contribution. They are supported by the findings presented in Chapters~\ref{ch:findings} and~\ref{ch:discussion}. The five included studies are referred to as Papers~I to~V and are introduced in Chapter~\ref{ch:studies}.

\begin{enumerate}[leftmargin=1em]

    \item \textbf{Graph-based representation learning for recovery and mapping.} The thesis develops and evaluates graph-based formulations for SAR (Papers~I and~II) and C2A mapping (Paper~III). These formulations explicitly represent implementation artifacts and their relations, and support learning without module labels for recovery and from a small labeled set for mapping. The studies compare alternative self-supervised objectives (Papers~I and~II), encoder architectures (Papers~II--V), dependency-relation representations (Papers~III and~IV), and message-passing configurations (Paper~III), and benchmark the resulting methods against established approaches (Papers~I--IV).

    \item \textbf{An empirical evaluation of architectural signals.} The thesis examines the architectural information carried by dependency structure and by lexical and contextual representations of source-code content, before folder organization, member-level detail, and message passing between neighboring files are added. Paper~IV examines how far the software dependency graph alone supports recovery. Paper~V compares structural, lexical, and contextual initial file representations with a graph-free classifier, so that the classifier receives no information from neighboring files beyond what each representation already encodes. Paper~V also examines whether a contextual code representation from a transformer model can be adapted using dependency information to reflect architectural proximity.
    
    \item \textbf{An analysis of the effect of graph structure on recovery and mapping.} The thesis adds folder organization and member-level detail to the file-level graph, makes dependency neighbors available through message passing, and examines whether each contributes beyond the initial file representation and whether the conclusions on the individual signals continue to hold. In recovery, Paper~IV examines folder nodes and Paper~I edge-level attributes. In mapping, Paper~V examines folder nodes, member nodes, and message passing, comparing each predictor with and without dependency-neighbor access, and Papers~III and~V compare aggregation directions. Where possible, these comparisons hold the file representation fixed, so that the contribution of the added structure can be separated from that of the representation.

    \item \textbf{A controlled cross-study evaluation.} The five studies use different benchmark scopes, which limit direct comparison of their results. The thesis, therefore, extends the evaluation of their methods to a common set of benchmark systems (Section~\ref{sec:cross_study_eval}). Recovery methods from Papers~I, II, and~IV are evaluated on fourteen systems using a common clustering algorithm and assessed by both agreement with reference decompositions and dependency cohesion. Mapping method comparisons build on Papers~III and~V and use ten systems under matched input representations, initial labeled sets, and self-training conditions. Mapping methods are assessed by the F1 score. Results are reported per system with significance tests and effect sizes.
\end{enumerate}

Together, the first three contributions treat model architecture, input representation, graph construction, and system structure as connected design decisions rather than independent sources of improvement.

\subsection{Software Architecture Recovery}

Traditional recovery methods treat software artifacts as a dependency graph and recover modules through several related paradigms. A first group formulates recovery as search over a modularization objective. Some methods optimize a single modularity criterion that favors high cohesion within modules and low coupling across them~\cite{bunch_sahc_nahc,dagc}, while others use multi-objective or evolutionary search to balance several criteria at once~\cite{mca_eca}. A second group clusters directly on dependency-derived similarities or information-theoretic criteria~\cite{cct,hcc_2019,limbo,wca}. ACDC~\cite{acdc} takes a different approach by building clusters from recurring subsystem patterns. A third group focuses on the clustering procedure itself. FCA~\cite{fca} speeds up clustering for large systems by working on the neighborhood degree matrix; Mohammadi and Izadkhah~\cite{neighborhood_tree_2019} build clusters from the neighborhoods of artifacts in the dependency graph, and Pourasghar et al.~\cite{gma_2021} use relationship depth. Overall, graph-based recovery methods can work well when dependencies reflect architectural structure, but their effectiveness depends on which dependency relations the graph includes and how the method uses them.

Semantic approaches use identifiers and comments instead of, or alongside, dependencies, and can outperform dependency-only methods in some systems~\cite{comparative_survey}. ARC~\cite{arc} uses latent Dirichlet allocation (LDA) to infer concerns from source text and combines them with structural information. ZBR and Risi et al. derive semantic similarities using lexical zones and latent semantic indexing (LSI), respectively~\cite{zbr,risi2012fold}, while Kargar et al.~\cite{kargar2017semantic} build a semantic dependency graph from lexical cues and optimize it by local search. Anquetil et al.~\cite{file_clustering} take a related but distinct approach by clustering files according to their names, using common substrings and concepts found in routine names or comments. Non-structural signals of this kind can be noisy in isolation, since reused terminology may span modules.

Hybrid approaches use multiple sources to capture complementary evidence. Some integrate structural and semantic relations before hierarchical clustering~\cite{sc_misra,escrc}. Others incorporate semantic information into search-based modularization, and NSGA-III also uses development change history~\cite{sadat2019multi,nsga3}. Puchala et al.~\cite{ensemble_recovery} combine several clustering results into a consensus solution, while Yang et al.~\cite{evol} use semantic cues to guide label propagation over the dependency graph. Naim et al.~\cite{naim2017cchd} combine structural and contextual information through coordinated clustering, refining the combination through incremental developer feedback. SADE~\cite{sade} and SARIF~\cite{sarif} combine signals in weighted dependency graphs and apply community detection. SARIF also incorporates directory similarity. These methods bring information together at different stages, from constructing relations and defining search objectives to guiding or combining clustering results. In most cases, the fusion is specified by a designed procedure, consensus rule, or heuristic weighting rather than learned jointly as a representation of the signals.

Representation learning has also been applied to recovery. NEGAR~\cite{negar} learns node representations from dependency graphs through random walks and clusters the resulting vectors. It applies this pipeline separately to graphs at different implementation levels and does not incorporate non-structural signals.

Another approach uses large language models to infer architectural structures and patterns from source code. SemArc~\cite{sar_sem} uses LLMs to identify implementation-level and architectural semantics, drawing on canonical architectural patterns as a knowledge base. It also incorporates explicit and implicit dependencies before applying component-as-anchor clustering. Amalfitano et al.~\cite{amalfitano2025automated} evaluate general-purpose LLMs on identifying implementation-level class diagrams, architectural and design patterns, and architectural styles. Their prompts include a self-reflection step to simulate iterative refinement. ArchAgent~\cite{archagent} combines static analysis and adaptive code segmentation with LLM-based synthesis to recover multi-view architectures from large, cross-repository codebases.

\subsection{Code-to-architecture Mapping}

Tzerpos and Holt~\cite{tzerpos1997orphan} introduced orphan adoption, the incremental assignment of unmapped entities to a documented architecture using naming and structural criteria. Christl et al.~\cite{christl2007automated} built on this with HuGMe, a semi-automatic method that extends a partial mapping through dependency-based attraction functions and leaves uncertain assignments for the architect to review. Bittencourt et al.~\cite{bittencourt_IR} later introduced the information-retrieval attraction functions IRAttract and LSIAttract, which use lexical similarity between entities and modules. InMap~\cite{InMap} takes an interactive recommendation approach, ranking candidate mappings from natural-language module descriptions. Like HuGMe, it keeps the architect involved, but through interactive recommendations rather than review of uncertain assignments. Together, these approaches rely on predefined criteria, attraction functions, or retrieval-based ranking rather than a jointly learned representation, the mapping analog of the fusion schemes above.

Learned classifiers provide another approach to mapping. Olsson et al.~\cite{olsson2022automatically} propose NBAttract, a semi-supervised Naive Bayes mapper that combines lexical and dependency information encoded via Concrete Dependency Abstraction (CDA). Florean et al.~\cite{florean2021textclassifierscomparison} compare text classifiers and text representations for the same task. Our earlier work~\cite{jabeen2025graph} represents dependencies directly as edges in homogeneous and dependency-type-aware graphs, in contrast to NBAttract's feature-based encoding. It evaluates graph convolutional network (GCN) variants and uses iterative pseudo-labeling to expand a small initial labeled set.

Some mapping studies use pretrained embeddings as classifier inputs, while others prompt general-purpose LLMs to produce mappings. Johansson et al.~\cite{johansson2024mapping} evaluate pretrained embeddings alongside TF-IDF and GloVe as input to method-level classifiers. In follow-up work, they examine how documentation granularity relates to classification performance with pretrained embeddings~\cite{johansson2026mapping}. Rukmono et al.~\cite{rukmono2024deductive} use chain-of-thought prompting with GPT-4 to map implementation units to a predefined reference architecture. Both approaches use lexical or semantic information, while typed dependencies remain implicit in their inputs.

\subsection{Limitations Across Recovery and Mapping}

Across recovery and mapping, many of the reviewed approaches rely on a single information source, combine sources through predefined rules, or use a fixed representation of each source within a learned model. Comparing the contributions of graph structure, directory organization, and source-code content requires varying these choices under matched conditions. The studies comprising this thesis examine how these signals can be represented, combined, and propagated for architecture recovery and C2A mapping.

\section[Representing Artifact Content]{Representing Artifact Content and Organization \label{sec:bg_content}}

A software system carries architectural evidence in more than one form. Its files and members are connected by static dependencies, but they also have names, occupy locations in the folder hierarchy that reflect how developers group related functionality~\cite{garcia2013}, and contain identifiers and comments that encode domain-specific knowledge~\cite{sarif}. In a representation learning framework, dependencies can be represented as graph relations, while the content associated with individual artifacts must be encoded numerically for a learning model to operate on. This section introduces the two families of representation used in the thesis: lexical and contextual.


\subsection{Lexical Representations \label{sec:bg_lexical}}

Lexical representations treat folder-path components and source-code identifiers as tokens. The simplest representation is a binary bag-of-words (BoW) vector, in which each dimension indicates whether a token is present in the artifact’s folder path or source code. Because it allocates one dimension to every vocabulary token, the representation becomes high-dimensional and sparse as the vocabulary grows. Word2Vec (W2V)~\cite{word2vec} instead learns a dense vector for each source-code identifier from a corpus of source-code tokens using a skip-gram model.

In skip-gram, each token is used to predict tokens occurring within a fixed context window. The vectors are trained to assign higher scores to observed token--context pairs than to randomly sampled pairs through negative sampling. As a result, tokens that occur in similar contexts receive similar vectors. An artifact’s Word2Vec representation is obtained by averaging the vectors of its source-code identifiers, producing a compact, fixed-dimensional encoding.

\subsection{Contextual Representations}

Contextual representations encode tokens in the context of the surrounding code rather than as an unordered collection of identifiers. The same identifier can therefore receive different representations in different contexts, whereas a trained Word2Vec model assigns a fixed vector to each token. Transformer-based encoders use attention to combine information from tokens within the input sequence, allowing each token’s representation to reflect how it is used in the code. Through pretraining on large corpora, these encoders learn patterns that can support different code analysis tasks. UniXcoder~\cite{unixcoder} is one such model, producing contextual token representations that can be pooled into a single vector for a code fragment.

A pretrained code encoder can be used without further training or adapted through fine-tuning. Fine-tuning adjusts its representations using a training objective and examples relevant to the target setting, which can include dependency information.

\section[Graph Representation Learning]{Graph-Based Representation Learning \label{sec:bg-gnn}}

Content encoders process artifacts individually, although their representations can capture dependency information introduced during fine-tuning. Graph-based representation learning uses the dependencies and containment relations between artifacts explicitly to learn node representations. The approaches used in this thesis fall into two groups: random-walk embeddings, which derive vectors directly from graph neighborhoods, and graph neural networks, which propagate and transform information along graph edges.

\subsection{Random-Walk Embeddings \label{sec:bg_random_walk}}
Random-walk methods learn node embeddings in two steps. First, they construct a corpus by sampling random walks over the graph, where each walk is a sequence of nodes. Node2Vec (N2V)~\cite{node2vec} samples walks over a homogeneous graph, which in this thesis is unweighted and undirected, whereas MetaPath2Vec (M2V)~\cite{metapath2vec} extends this to heterogeneous graphs by constraining walks to follow a predefined sequence of node and relation types. Second, a skip-gram model (see Section~\ref{sec:bg_lexical}) is trained over this corpus, treating the nodes within a fixed context window of a target node as its observed context, so that nodes with similar walk contexts receive similar embeddings. Walk length, context window, and the number of walks per node determine which nodes are treated as similar. These methods learn from walk co-occurrence alone and therefore do not jointly incorporate artifact content.

\subsection{Graph Neural Networks \label{sec:bg_gnns}}
Graph neural networks (GNNs) provide a common framework for learning from artifact-level information and graph structure, producing node representations shaped by both. A GNN encoder maps each node, together with its initial representation and graph neighborhood, to a vector through message passing~\cite{neuralMP}. At each layer, a node aggregates the current representations of its neighbors, combines them with its own, and applies a learned transformation. GNN architectures differ primarily in how they transform and aggregate these messages, and this thesis uses three variants.

The graph convolutional network~\cite{gcn} aggregates neighboring representations through degree-normalized message passing, which helps prevent high-degree nodes from dominating solely because they have many dependencies. The graph attention network (GAT)~\cite{gat} instead learns attention weights over neighbors, allowing their contributions to differ according to their representations. Both encoders can be applied either to a graph in which dependency types are collapsed or to a multi-relational graph with relation-specific parameters. When the graph contains multiple node types and typed relations, this thesis also uses the heterogeneous graph transformer (HGT)~\cite{hgt}, which parameterizes attention by meta-relation. Thus, the contribution of a neighbor depends jointly on the source-node type, target-node type, and edge type.
\subsection{Graph Properties and Learning \label{sec:bg_properties}}

Two properties are particularly relevant to how well graph-based encoders can support downstream tasks: homophily and structural reach. A graph is homophilic with respect to a labeling when connected nodes tend to share a label. Under homophily, neighborhood aggregation reinforces label-consistent information; under heterophily, it mixes information from different labels and may obscure distinctions needed by the downstream task~\cite{gnn_homophily}. Formally, let $G=(V,E)$ be a graph in which each node $v \in V$ has a label $y_v$. Homophily $\mathcal{H}$ is the proportion of edges whose two endpoints have the same label,
\begin{equation}
\mathcal{H} = \frac{|\{e=(u,v) \in E : y_u = y_v\}|}{|E|},
\label{eq:homophily}
\end{equation}
so that $\mathcal{H}=0$ means every edge connects nodes with different labels and $\mathcal{H}=1$ means every edge connects nodes with the same label~\cite{gnn_homophily}. For software systems, the nodes are files, the edges are static dependencies between them merged across dependency types, and the label is the ground-truth module. In this setting, homophily relates to cohesion and coupling by measuring the proportion of dependencies that remain within modules rather than cross module boundaries. It provides an overall measure of this balance, but does not distinguish how those dependencies are distributed across individual modules.

Since $\mathcal{H}$ is computed from the reference decomposition, it can be determined only once such a decomposition exists. The concentration of dependencies within modules varies across systems, and so does the usefulness of dependency-driven random walks and message passing.

The second property is the structural reach of the encoder, which we use to mean the set of nodes that can contribute information to a node representation. For an $L$-layer message-passing encoder, this is the node's $L$-hop neighborhood. Reach describes which nodes can contribute by construction, rather than how much they contribute in practice. Increasing depth extends this reach, but repeated aggregation can make node representations progressively less distinguishable, an effect known as over-smoothing~\cite{gnn_oversmoothing}. GNN encoders are therefore commonly kept shallow.

With a shallow encoder, access to more distant architectural information depends on how the input graph connects the nodes. Changing these connections can make that information reachable within fewer message-passing steps. Random-walk embeddings can capture longer-range structural context through sampled walks, although they do not propagate artifact-level representations along the graph.

Two further techniques alter the structural information available to a shallow encoder without increasing its number of message-passing layers. Laplacian positional encoding (LPE) augments each node representation with leading eigenvectors of the graph Laplacian, giving the encoder information about the node's structural position before message passing begins~\cite{lpe}. Graph diffusion convolution (GDC)~\cite{gdc} rewires the input graph using personalized PageRank (PPR), connecting diffusion-close nodes directly and assigning the resulting edges diffusion-derived weights. This makes multi-hop structural proximity available within a fixed number of message-passing layers.

\subsection{Learning Paradigms \label{sec:bg_learning}}

The encoder architecture determines how information propagates through the graph, but not what drives learning. That role belongs to the training objective, which depends on the supervision available. The studies in this thesis use two learning settings that reflect the recovery and mapping tasks.

\paragraph{Architecture recovery.} No module labels are available during recovery, so the studies use self-supervised learning, in which the model learns from an auxiliary signal derived from the graph itself. These methods construct positive and negative training examples from the graph, with the examples differing between methods. Binary cross-entropy (BCE) measures how well the model distinguishes positive from negative examples. For a single example, it is defined as:
\begin{equation}
    \mathcal{L}_{\mathrm{BCE}} = -\left[y\log\hat{y} + (1-y)\log(1-\hat{y})\right],
    \label{eq:bce}
\end{equation}
where $y \in \{0,1\}$ is the target and $\hat{y}$ is the predicted probability.

Contrastive learning trains representations by contrasting positive and negative pairs. Deep Graph Infomax (DGI)~\cite{dgi} applies this principle to graphs by treating node--summary pairs in the original graph as positive and pairs constructed from a corrupted view as negative. Graph autoencoders (GAE)~\cite{gae} instead learn node representations by reconstructing observed graph edges, treating observed edges as positives and sampled non-edges as negatives. Their variational form (VGAE)~\cite{gae} models each node's latent representation as a Gaussian distribution rather than a single vector and adds a Kullback--Leibler (KL) divergence term that penalizes deviations from a standard normal prior. Random-walk methods learn without module labels through the skip-gram objective described in Section~\ref{sec:bg_random_walk}.

The learned embeddings are then partitioned with a clustering algorithm, typically agglomerative hierarchical clustering~\cite{agglomerative}, for architecture recovery. This clustering step is unsupervised: it derives module groups from similarity between embeddings. The number of clusters is either selected automatically from a predefined search range or fixed in advance.

\paragraph{Code-to-architecture mapping.} Mapping starts from known module assignments for a limited number of files, so the studies train a classifier on these labeled files with supervised learning. Because the module set is known and fixed, the classifier assigns each file to one of the $K$ predefined modules through a softmax layer, which yields a probability distribution over the modules, and the highest softmax probability of a prediction is its confidence. It is trained with categorical cross-entropy (CCE), $-\sum_{k=1}^{K} y_k\log\hat{y}_k$, which for a one-hot target is the negative log-probability assigned to the true module.

Unlabeled files can also contribute through iterative self-training~\cite{lee2013pseudo}, which Paper~III applies on top of supervised training. The classifier assigns pseudo-labels to unlabeled files whose confidence exceeds a predefined threshold, retrains on the labeled and pseudo-labeled files, and repeats over successive rounds until no prediction meets the criterion or a maximum number of rounds is reached.

\section[Evaluation and Ground Truth]{Evaluation and Ground Truth}
\label{sec:bg-eval}

The studies in this thesis evaluate their outputs against reference decompositions from published, expert-validated benchmarks, supporting comparison with prior work. Recovery produces a partition whose cluster labels have no predefined meaning, whereas mapping assigns files to known architectural modules. Recovery is therefore evaluated through partition-agreement metrics and mapping through conventional classification metrics. This section introduces these measures and discusses how reference decompositions should be understood as ground truth. The provenance of the specific reference mappings is discussed in Chapter~\ref{ch:methodology}.

A reference decomposition provides an established basis for comparison, but it need not be the only reasonable architectural interpretation of a system. Experts may disagree on architectural boundaries and design intent~\cite{garcia2013}, so a recovered decomposition can differ from the reference without necessarily being wrong.

Complementary metrics assess different aspects of a recovered decomposition. MoJoFM, A2A, and \cc{} measure alignment with a reference decomposition. The adjusted Rand index (ARI)~\cite{ari} measures partition agreement while correcting for chance. TurboMQ provides a complementary, reference-independent measure of modularization quality based on the dependency graph.

MoJoFM~\cite{mojofm} is widely used in architecture recovery. It counts the minimum number of move and join operations needed to transform the recovered partition into the reference partition, normalized by the maximum possible number of such operations. Because its join operations are comparatively cheap, MoJoFM is less sensitive to over-fragmentation: many small clusters can still score well when they broadly align with the reference. A2A~\cite{a2a} extends MoJoFM with costs for adding, removing, and moving entities and clusters. It can assign a high score to two architectures that are structurally quite different, overestimating their similarity~\cite{turbomq}.

\cc{}~\cite{c2c} measures the percentage of reference modules that are sufficiently covered by a recovered module, where coverage is judged against a threshold on the overlap between the two; conventional thresholds of 0.10, 0.33, and 0.50 correspond to weak, moderate, and majority matches. This makes it sensitive to fragmentation: a reference module split across several recovered modules does not count as matched if none of them meets the chosen overlap threshold, even where individual file assignments look reasonable under a different metric. ARI ranges from $-1$ to $1$, where $0$ is the agreement expected by chance.

Unlike the metrics above, which measure alignment with the reference decomposition, TurboMQ~\cite{turbomq} measures modularity: it rewards intra-cluster cohesion and penalizes inter-cluster coupling, computed directly on the dependency graph without reference to any external partition. TurboMQ can favor decompositions with many clusters. Normalized TurboMQ (\tmq{}) divides the TurboMQ score by the number of recovered clusters to reduce this bias.

The reference-agreement metrics described above assess how closely a recovered decomposition matches an expert-produced reference, whereas TurboMQ evaluates its dependency structure. Expert-produced references can reflect responsibilities and project organization identified through documentation, source code, and knowledge of the system. These boundaries need not coincide with groups of densely connected files, since shared utilities and libraries can create dependencies across architectural modules~\cite{garcia2013}. A reference decomposition therefore need not maximize dependency modularity, and a recovered decomposition can score well on one kind of measure without scoring well on the other.

For mapping, the evaluation is a per-file classification into known modules, and the standard metrics apply directly. Precision, recall, and their harmonic mean F1 are reported per module and aggregated at the macro and micro level. The macro-average treats every module equally and therefore surfaces performance on small modules that would be hidden by a micro-average dominated by large ones. Reporting both reveals differences in performance across modules of different sizes.

\chapter{Problem Formulation and Research Objectives \label{ch:research_objective}}
\chaptertoc

This chapter formalizes the research problem addressed in this thesis and defines the objectives for investigating it. It first presents software architecture recovery and C2A mapping as related file-to-module assignment problems within a common graph-based representation-learning framework. It then states the research objectives and associated research questions.

\section{Problem Formulation}
\label{sec:problem-formulation}
Architecture recovery and C2A mapping both assign source-code files to architectural modules, but differ in the architectural information available. This thesis approaches recovery by learning file representations without module labels and clustering them into modules. In C2A mapping, the target modules and a subset of file assignments are known, and the task is to predict the remaining assignments. Both tasks are formulated here using a common graph representation.

Despite this difference in supervision, both tasks draw on dependencies, project organization, and source-code content as discussed in Section~\ref{sec:intro-motivation}. This thesis uses graph-based representation learning to combine these signals as evidence of module membership.

Accordingly, a software system is represented as a graph:
\begin{equation}
\mathcal{G} = (\mathcal{V}, \mathcal{E}, \mathcal{A}, \mathcal{R}, \mathbf{X}),
\label{eq:software_graph}
\end{equation}
where $\mathcal{V}$ and $\mathcal{E}$ are the node and edge sets, $\mathcal{A}$ and $\mathcal{R}$ are the node and relation types, and $\mathbf{X}$ denotes node attributes. The maps $\tau: \mathcal{V} \rightarrow \mathcal{A}$ and $\phi: \mathcal{E} \rightarrow \mathcal{R}$ assign types to nodes and edges. Structure-only settings use no lexical or folder attributes. File nodes form the subset $\mathcal{V}_{\texttt{file}} \subseteq \mathcal{V}$.

The graph is homogeneous when $|\mathcal{A}| = |\mathcal{R}| = 1$, and heterogeneous otherwise. Its simplest form is a software dependency graph (SDG), containing only file nodes and a single dependency relation type. Preserving dependency types increases $|\mathcal{R}|$, while adding folder and member nodes increases both $|\mathcal{A}|$ and $|\mathcal{R}|$. Folder and member nodes provide context for learning file representations; only file nodes are assigned to architectural modules.

Formally, for recovery, we learn an encoder $f_{\theta}$ in a self-supervised manner:
\begin{equation}
f_{\theta}: \mathcal{G}\;\longrightarrow\;\mathbf{Z}\in\mathbb{R}^{|\mathcal{V}_{\texttt{file}}|\times d},
\label{eq:sar}
\end{equation}
that maps each source code file $i \in \mathcal{V}_{\texttt{file}}$ to a $d$-dimensional embedding $\mathbf{z}_i \in \mathbb{R}^{d}$, where $\theta$ denotes the learnable parameters. The resulting file embeddings are clustered into a recovered architectural decomposition $\hat{\mathcal{C}}$, which partitions the source code files into $m$ disjoint modules:
\begin{equation}
\hat{\mathcal{C}} = \{C_1, \dots, C_m\}.
\label{eq:sar-partition}
\end{equation}

In C2A mapping, a set of target modules $\mathcal{C} = \{C_1, \dots, C_m\}$ is known, together with a labeled subset of files $\mathcal{L} \subseteq \mathcal{V}_{\texttt{file}}$ and their module assignments $Y_{\mathcal{L}}$. The task is to learn:
%
\begin{equation}
f_{\theta}: (\mathcal{G},\;\mathcal{L},\;Y_{\mathcal{L}})\;\longrightarrow\;\hat{Y}_{\mathcal{U}},
\label{eq:c2a}
\end{equation}
for the unlabeled files $\mathcal{U} = \mathcal{V}_{\texttt{file}} \setminus \mathcal{L}$. The model is trained on the labeled files, and the supervision is limited to this subset. Training may additionally use the model's confident predictions on unlabeled files as pseudo-labels. The setting is transductive: all files, labeled and unlabeled, are part of $\mathcal{G}$ during training.

The two problems use the same implementation signals, but differ in how representations are learned and how their contribution can be assessed. In recovery, module labels are unavailable, so representations are shaped by the graph construction, the input representations, and a self-supervised objective. The final decomposition also depends on the clustering procedure and granularity. In C2A mapping, known file-to-module assignments provide task-specific supervision, allowing matched configurations to be compared using per-file classification metrics. Mapping thus provides a complementary setting for examining whether individual signals help predict an existing decomposition. However, its results depend on the number of initially labeled files, their coverage and distribution across modules, and the training procedure. A signal's usefulness or ranking in one task therefore does not necessarily carry over to the other.

\section{Research Objectives}
\label{sec:research-objectives}

The research aim is operationalized through three objectives that progress from joint representation learning to examining individual signals and file representations, and then to their interaction within richer graphs. Objective 1 designs, compares, and benchmarks graph-based methods for recovery and mapping by combining dependency, organizational, and lexical signals. This examines their joint usefulness, but not their individual contributions. Objective 2 therefore examines the architectural information these signals and representations carry, including how source-code content should be represented. Objective 3 investigates how their usefulness changes as structural context is added and whether findings from Objectives 1 and 2 remain valid.

\subsection[Representation Learning for Recovery and Mapping]{Representation Learning for Architecture Recovery and C2A Mapping}
\label{sec:obj_1}

\begin{GrayBox}{Objective~1}
To design, compare, and benchmark graph-based representation learning methods for architecture recovery and code-to-architecture mapping.
\end{GrayBox}
\begin{enumerate}[label=RQ1.\arabic*, leftmargin=3em, itemsep=0.1pt]
    \item How can implementation-level signals be combined into a joint representation for architecture recovery and mapping?
    \item How does modeling dependency types as separate relations compare with merging them into a single relation?
    \item How sensitive is the learned representation to encoder architecture, learning objective, and model depth?
\end{enumerate}
This objective is addressed through comparisons across recovery and mapping studies on file-level graphs. Most comparisons jointly encode folder, lexical, and dependency signals within one encoder. The comparisons cover GCN, GAT, and HGT encoders and merged versus relation-specific dependencies. Recovery experiments compare contrastive and reconstruction objectives using the same encoder, inputs, and benchmark systems. Mapping studies also vary model depth; one study and its cross-study extension use inputs without folder signals.
% _______________________
\subsection{Architectural Information in Implementation Signals}
\label{sec:obj_2}

\begin{GrayBox}{Objective~2}
To determine what architectural information dependency structure and individual file representations provide, and how source-code content should be represented.
\end{GrayBox}
\begin{enumerate}[label=RQ2.\arabic*, leftmargin=3em, itemsep=-0.05pt]
    \item How far can dependency structure alone support architecture recovery, in agreement with the reference and in dependency cohesion?
    \item How does dependency-guided adaptation of a contextual code representation affect the architectural signal it carries?
    \item How do structural, lexical, and contextual file representations compare in mapping without message passing?
\end{enumerate}
This objective examines the architectural information carried by individual implementation signals. In recovery, it uses dependency structure alone on the homogeneous SDG, without lexical or folder information, and examines how much structural context is needed across systems. In mapping, it compares file representations without adding folder organization, member-level detail, or SDG-based message passing. These representations include Word2Vec, zero-shot UniXcoder, Node2Vec, and UniXcoder fine-tuned through SDG-guided contrastive learning without module labels. The latter two incorporate dependency information during representation learning. A multilayer perceptron (MLP) classifier uses each file's representation independently, so it can access dependency information only if that information is already encoded in the representation.
% ______________________
\subsection{Interaction Between Input Signals and Graph Structure}
\label{sec:obj_3}

\begin{GrayBox}{Objective~3}
To determine how the contribution of file representations changes with dependency-based message passing, folder organization, and member-level graph detail, and whether findings from Objectives~1 and~2 remain valid.
\end{GrayBox}

\begin{enumerate}[label=RQ3.\arabic*, leftmargin=3em, itemsep=-0.05pt]
    \item How does the usefulness of message passing over dependency neighbors vary across predictors, aggregation directions, and file representations?
    \item How does adding folder organization to the graph change what the file representations contribute to recovery and mapping?
    \item How does performance differ with and without member-level nodes and edge-level interaction details?
\end{enumerate}
This objective examines how additional graph structure changes the contribution of file representations. In recovery, folder nodes and containment meta-relations are added to the SDG and evaluated through message passing or random walks; edge attributes describing the member-level interactions behind each dependency, including their type and frequency, are examined separately. In mapping, an MLP and graph-based neural predictors are compared, and each predictor is evaluated with and without access to dependency neighbors while holding file representations fixed. Aggregation direction is also varied. Folder and member nodes are evaluated with Word2Vec, Node2Vec, and fine-tuned UniXcoder. Member nodes also change how lexical and contextual content enters the model, and a rule based on the directory hierarchy and initial labels provides a reference.

\phantomsection
\subsection[Paper~I: Architecture Recovery]{Paper~I.\quad Graph Representation Learning for Software Architecture Recovery}
\label{sec:overview-arl}

The first study~\cite{arl_2026} establishes the initial feasibility of learning architectural representations from a multi-relational software dependency graph for architecture recovery. Each dependency type is modeled as a separate directed relation among source-code files, while node features combine folder-hierarchy tokens with code identifiers not involved in inter-file dependencies. Relation-specific GAT encoders produce file representations that are trained without architectural labels using a contrastive objective and subsequently clustered to recover modules. The study also examines whether member-level interaction attributes add architectural information beyond the presence of a dependency.
 
The study evaluates the proposed approach on four systems against SARIF~\cite{sarif}, a hand-tuned information-fusion baseline that combines dependency, textual, and directory signals through manually designed similarity functions. The proposed approach reaches higher MoJoFM than SARIF on all four systems.

\phantomsection
\subsection[Paper~II: Architecture Recovery]{Paper~II.\quad GAER: Graph Auto-Encoders for Unsupervised Software Architecture Recovery}
\label{sec:overview-gaer}

The second study~\cite{gaer} extends the investigation of Paper~I to a reconstruction-based learning approach and a broader empirical setting. GAER retains the multi-relational dependency graph but replaces contrastive learning with a graph autoencoder trained to reconstruct observed dependencies. Code identifiers are now embedded with Word2Vec rather than encoded as binary vectors, while directory tokens remain binary-encoded. The study compares GCN and GAT encoders before clustering the learned representations into architectural modules.
 
The study evaluates ten benchmark systems against eight established dependency-based, semantic, structural representation learning, and hybrid recovery approaches. GAER achieves higher or comparable ground-truth alignment across most systems for MoJoFM, A2A, \cc{}, and ARI.

\phantomsection
\subsection[Paper~III: C2A Mapping]{Paper~III.\quad When Does the Dependency Graph Help Code-to-Architecture Mapping?}
\label{sec:overview-c2a}

The third study~\cite{c2a_mapping} is an extended version of an earlier mapping paper~\cite{jabeen2025graph}. It shifts from unsupervised architecture recovery to C2A mapping, in which the target modules are known, and a limited set of files is initially labeled. It reuses the graph construction and node features of Paper~II, expanding the labeled set into a full mapping via iterative self-training. The study compares GCN and GAT models with an MLP that uses the same file features, classifier, and self-training procedure. It further examines the effect of preserving dependency types, message-passing depth, and aggregation direction.
 
Across ten benchmark systems, all learned approaches outperform the Naive Bayes mapping baseline~\cite{olsson2022automatically}. The gain of GAT and GCN over the MLP varies by system and is largest on Chromium, the largest system.

\phantomsection
\subsection[Paper~IV: Architecture Recovery]{Paper~IV.\quad Graph Embeddings for Software Architecture Recovery}
\label{sec:overview-structsar}

The fourth study returns to architecture recovery but isolates the value of structural and organizational information by removing lexical file features~\cite{structsar}. Unlike the first three studies, it learns representations from graph structure alone. The study first evaluates recovery from a homogeneous dependency graph using Node2Vec, a GAT encoder trained within a variational graph autoencoder, and the same encoder applied to a graph rewired by PPR diffusion (GAT-DC). It then extends the graph with folder nodes and containment relations, comparing the dependency structure alone against the dependency structure combined with developer-defined folder organization, using MetaPath2Vec, a heterogeneous GAT (HGAT), and a variant that preserves dependency types rather than merging them (HGAT-TD).
 
The study evaluates eleven systems against four classical dependency-only recovery baselines. The dependency-only GAT-DC and Node2Vec outperform these baselines on most systems and metrics.

\phantomsection
\subsection[Paper~V: C2A Mapping]{Paper~V.\quad What Carries Architectural Signal? A Code-to-Architecture Mapping Study}
\label{sec:overview-hetmap}

The fifth study examines which implementation signals contribute to C2A mapping and how their usefulness changes with graph structure and message passing~\cite{hetmap}. It compares structural Node2Vec, lexical Word2Vec, and contextual UniXcoder file representations, with UniXcoder evaluated before and after dependency-guided contrastive fine-tuning. Each representation is first evaluated using an MLP. Node2Vec, Word2Vec, and fine-tuned UniXcoder then initialize HGT on four graph configurations: files only, files with folders, files with members, and the full folder-file-member graph, with dependencies merged into a single relation type. Each member node summarizes the program members of one file. A GAT on the file-level dependency graph is evaluated as a second message-passing predictor.
 
The study uses the ten systems and labeled sets of Paper~III. The MLP is the baseline for the graph configurations, and a directory-hierarchy rule is the reference for folder-augmented configurations. The rule assigns an unlabeled file the most common module among the labeled files in its directory, backing off to progressively larger enclosing subtrees when the directory has no labeled file associated with it.

\chapter{Research Method \label{ch:methodology}}
\chaptertoc

This chapter describes the research method used to investigate architecture recovery and C2A mapping. It defines the research design and the graph-based representation-learning design space, then describes the input signals, learning settings, and controlled-comparison logic used across the studies. It also presents the benchmark systems and evaluation protocol, including the sampling of labeled files and statistical analysis. Finally, it describes the additional cross-study evaluation design.
\section{Research Design \label{sec:research_design}}

This thesis combines method development with empirical evaluation. Each study develops and evaluates a graph-based representation learning method for architecture recovery or C2A mapping. The studies investigate what architectural information is carried by implementation signals, including dependency structure, project organization, and code content, and the system conditions under which these signals support architectural analysis. Comparisons with established baselines assess whether the resulting methods are competitive, whereas controlled comparisons between graph configurations, input representations, and learning mechanisms examine the contribution of each.

\subsection{Design Space\label{sec:design_space}}

Architecture recovery and mapping are studied through a common graph-based representation-learning framework. The choices investigated across the thesis define a design space with four dimensions: graph topology, relation modeling, input representation, and learning mechanism, summarized in Figure~\ref{fig:design_space}. These dimensions are analytically distinct but not always experimentally independent: adding a node type usually requires a new relation type to connect it to the rest of the graph.
 
Graph topology determines which software artifacts are represented as nodes. The simplest configuration contains only file nodes. Richer variants add folder nodes, one per directory, member nodes that aggregate the program elements contained in each file, or include both folder and member nodes together. Relation modeling determines how these nodes are connected. Static dependencies may be merged into a single relation or preserved as typed relations such as \emph{call}, \emph{import}, and \emph{inheritance}. Graphs containing additional artifact types also include organizational and containment meta-relations, such as folder-to-folder, folder-to-file, and file-to-member relations.
 
Input representation determines what information is available to the nodes before message passing. Nodes may start with learnable identity embeddings or with features derived from dependency structure, folder organization, or code content. These features range from token-based representations and structural encodings to pretrained contextual code embeddings.
 
The learning mechanism determines how these inputs and graph relations are used to learn file representations. The studies compare random-walk methods and graph neural networks, with learning objectives suited to recovery or mapping.

\subsection{Research Trajectory \label{sec:research_trajectory}}

The studies progressively examine how dependency structure, project organization, and code content contribute to recovery and mapping. Each study addresses a question left open by earlier work and informs the choices investigated in the next. Together, they cover an expanding range of graph configurations, input representations, and learning mechanisms.
 
The prior approach, NEGAR~\cite{negar}, evaluates dependency types through separate pipelines and uses neither folder organization nor lexical information, leaving open whether typed dependencies can be modeled jointly and whether organizational and lexical signals provide complementary evidence for recovery. Papers~I and II take a first step on this question with a multi-relational file-level graph. Both fuse folder-path and code-identifier tokens as node features, so the contribution of each source cannot yet be separated from the others.

Paper~III keeps the graph and feature construction of Paper~II, apart from the Word2Vec settings, and moves to a semi-supervised setting, formulating mapping as node classification. It introduces an MLP baseline, trained under the same features and self-training procedure, to compare GNN-based prediction against feature-only prediction.

Paper~IV, a further recovery study, returns to dependency structure and project organization, without lexical features. Removing the lexical features allows the contribution of project organization to be assessed without the fused signal of the earlier studies. It compares dependency-only file graphs against folder-augmented heterogeneous graphs under matched conditions, using both random-walk and graph-attention learners, and evaluates ways to extend the effective reach of message passing.
 
Paper~V extends the mapping design by introducing a dependency-guided contextual code representation and by expanding the graph to include folder and member nodes. It compares structural, lexical, and contextual representations with and without message passing, and across graph variants that add or remove folder and member nodes, under one matched supervised mapping setting.

\subsection{Graph Construction}\label{sec:graph_construction}
Across the five studies, graph topology evolves from file-level dependency graphs to representations that additionally include folder and member nodes. Files remain the targets of recovery or mapping, whereas folder and member nodes provide contextual information through message passing. Static dependencies between code entities are extracted with the multilingual analysis tool Depends~\cite{depends} and aggregated to the file level. Papers~I, II, and~III use the file-only configuration, with static dependencies kept as separate typed relations. Paper~III further tests a merged-relation variant to determine whether relation-specific message passing contributes to mapping.

Papers~IV and~V add context through folder nodes, and Paper~V also through member nodes. Both merge dependencies into a single relation type. Paper~IV compares the file-only graph with a folder-augmented configuration to isolate the contribution of project organization, with a typed-dependency variant as an ablation within the folder-augmented graph. Paper~V adds summarized member nodes, each representing the program elements contained in one file, and evaluates four graph variants: file only, file with folders, file with members, and the complete file--folder--member graph. In the complete graph, dependencies keep their file- or member-level endpoints; when member nodes are removed, member endpoints are projected onto their containing files.

\subsection{Node Feature Initialization}
\label{sec:node_feature_initialization}

Node-feature initialization operationalizes the input-representation dimension of the design space. Papers~II and~III initialize each file node by concatenating a binary BoW representation of its folder path with the $\ell_2$-normalized mean of Word2Vec embeddings for its code identifiers. Paper~I uses the same sources but represents both folder path and identifier tokens as $\ell_2$-normalized binary BoW vectors. Organizational and lexical information therefore enter these models as a fixed input.

Paper~IV uses no external lexical or organizational features. Instead, each node type receives a learnable identity embedding trained jointly with the model; file nodes additionally receive LPE, which supplies structural position in the dependency graph. Its Node2Vec and MetaPath2Vec baselines use no input feature vectors, since they learn representations directly from random-walk co-occurrence.

Paper~V treats node initialization as the object of study rather than a fixed choice. File and member nodes use lexical Word2Vec embeddings over identifiers, structural Node2Vec embeddings from the dependency graph, or contextual UniXcoder embeddings from code text extracted from source files, evaluated in zero-shot (\zs{}) and dependency-guided fine-tuned (\ft{}) forms. Where folder nodes are included, they are consistently initialized using binary BoW vectors derived from folder-path tokens. Paper~V therefore varies the representation of file- and member-level information while holding folder-node initialization constant.

Input text is extracted using Tree-sitter~\cite{tree_sitter} with the Java, C, or C++ grammar matching each file. The syntax tree guides fragment selection but is not itself passed to the encoder. A file-level view contains type declarations, fields or global variables, and constructor signatures with short body excerpts where applicable. A member-level view contains method and function declarations and definitions. Each file receives one vector per view. The file-level view is encoded as a single input, while the member-level vector is obtained by mean-pooling representations of overlapping text chunks.

In zero-shot use, UniXcoder encodes these views without further training. It is also fine-tuned separately for each system on file-level views using a contrastive objective~\cite{infonce} to incorporate dependency structure. Positive pairs are drawn from each file's two-hop dependency neighborhood, falling back to a direct neighbor when no two-hop candidate exists. Other files in the batch serve as negatives, except directly connected files, which are masked unless selected as the positive pair. Module labels are not used in this loss. The resulting model encodes both views, although fine-tuning uses only file-level text.

\subsection{Edge Attributes}\label{sec:edge_attributes}
Edge attributes form a narrower axis of the design space and are used beyond relation type in only Papers~I and~IV. In the remaining studies, edges are defined only by their relation type. Paper~I evaluates a variant that augments file-level dependency edges with attributes describing the member-level interactions that produce them: an $\ell_2$-normalized binary encoding of interaction type and a log-normalized interaction frequency. This tests whether the origin and frequency of a dependency provide information beyond its typed presence.
 
Paper~IV uses edge attributes differently in its diffusion variant. GDC rewires the file graph using PPR and assigns each rewired edge a scalar diffusion weight, which biases attention towards diffusion-close neighbors. Unlike the attributes of Paper~I, these weights are derived from graph topology rather than from additional implementation information. They therefore extend the effective reach of message passing rather than introduce a separate input signal.

\section{Learning Settings}
\label{sec:learning_settings}

Once the graph and node features are constructed, the studies differ in how they learn file representations and how these representations are used to obtain module assignments. This difference follows the two tasks: recovery methods learn embeddings and cluster them into modules, whereas mapping methods predict assignments to a predefined module set. Table~\ref{tab:learning_settings} summarizes the encoder, learning objective, and training configuration used in each study.

For multi-relational graphs, GCN and GAT use separate layers for each dependency type and aggregate their outputs. HGT instead incorporates node and relation types directly in its attention mechanism, processing the relation types jointly within each layer.

In the recovery studies (Papers~I, II, and~IV), no module labels are available during training. Paper~I learns file embeddings using a GAT with a contrastive objective, while Paper~II compares GCN and GAT encoders trained through graph reconstruction against a Node2Vec baseline that follows NEGAR~\cite{negar}. Paper~IV compares random-walk methods with GAT-based encoders trained within a variational graph autoencoder. Its graph-attention variants examine diffusion, folder context, and typed dependencies.
 
The learned file embeddings are then clustered into modules using agglomerative hierarchical clustering with Ward linkage, except for the Node2Vec embeddings of Papers~II and~IV, which use k-means, following NEGAR~\cite{negar}. The number of clusters is either selected automatically or set to the number of ground-truth modules, as in the main evaluation of Paper~IV. Recovery therefore infers the file assignments and, unless the number of clusters is fixed, also the number of modules.

In the mapping studies (Papers~III and~V), the target modules are known, and a small set of files is labeled with their ground-truth assignments. Paper~III compares GCN, GAT, and MLP models under the same feature representation and training procedure, and uses iterative self-training to expand the labeled set. Paper~V compares MLP, GAT, and HGT. The baseline MLP uses file features alone, GAT uses the file-only graph, and HGT is evaluated on all four graph variants. Additional comparisons examine dependency-neighbor aggregation, including a neighbor MLP that receives each file's own vector concatenated with the mean vector of its dependency neighbors. Paper~V trains each model on the labeled files for 200 epochs without self-training. It uses the same loss function, optimizer, and learning rate as Paper~III, with encoder configurations given in Table~\ref{tab:learning_settings}. Mapping therefore predicts file assignments to a predefined module set.

\subsection{Controlled-Comparison Logic \label{sec:controlled_comparison}}
The studies examine selected choices within the design space through controlled comparisons. Some choices are coupled, since adding folder or member nodes also introduces relations and changes the paths available for message passing. A full factorial evaluation of all combinations would be computationally prohibitive. Each comparison therefore varies one or two choices while keeping the remaining conditions fixed where possible, allowing differences in outcome to be related to the choices under investigation.
 
The mapping studies compare graph-based encoders with an MLP using the same input features and training procedure. These comparisons are consistent with a contribution of dependency-graph information, but they change the predictor together with the available structure. Paper~IV compares a dependency-only graph with the same graph augmented by folder nodes while keeping the learning setting fixed, testing the contribution of organizational structure in the absence of lexical features. Paper~V extends this logic by varying feature initialization and, with HGT, graph structure across file-only, folder-augmented, member-augmented, and combined graph variants. It also enables and disables dependency neighbors within each predictor while holding the file representations fixed. This makes it possible to examine the effects of input features and structural additions separately and, where combinations are included, their interaction.

\section{Evaluation Protocol \label{sec:eval-protocol}}

Every controlled comparison in the thesis follows the same evaluation protocol. Model initialization and training, and, in the mapping studies, selection of the labeled set, involve randomness, so a single run cannot distinguish a systematic difference between configurations from ordinary run-to-run variation. Each stochastic method--configuration pair is therefore run 100 times. Results are summarized by the median across runs rather than the mean, because the median is robust to occasional outlying runs.

\subsection{Labeled Training Sets}
In the mapping studies, each labeled set begins with a uniform random sample of 5\% of a system's files, bounded between 30 and 200 files. One file is then added from each module not represented in that sample. The floor and cap therefore apply to the random sample before these module-coverage additions, and the final labeled set can exceed the bounded sample size. Papers~III and~V use the same labeled sets, which self-training expands only in Paper~III.
 
The 30-file floor applies to Commons-Imaging, SweetHome-3D, Bash, HDF, and HDC, corresponding to approximately 9--20\% of their files before module-coverage additions. The 200-file cap applies only to Chromium, corresponding to approximately 1\% of its files. For ArgoUML, JabRef, Lucene, and TeamMates, the random sample follows the nominal 5\% rule. The experiments therefore use a bounded labeling budget rather than a constant labeled proportion: smaller systems receive a larger labeled share, while Chromium receives a smaller share. Comparisons within each system use the same labeled sets, but cross-system performance differences must be interpreted in light of these different labeled proportions.
 
The mapping studies therefore use ten of the fourteen systems. ArchStudio4, Hadoop, and OODT are excluded because representing every module would require labeling approximately 10--25\% of their files, and Libxml is excluded because the 30-file floor alone would label approximately 37\% of its files.

\subsection{Statistical Analysis \label{sec:stat_analysis}}

To assess the statistical significance of observed differences between methods or configurations, nonparametric tests are used because metric values across repeated runs are not necessarily normally distributed. The recovery studies compare independent distributions of one hundred runs per configuration and use the Mann--Whitney $U$ test~\cite{mann}. In the mapping studies, the compared configurations use the same labeled set in each run, producing paired observations. These comparisons use the Wilcoxon signed-rank test~\cite{wilcoxon}. Where a recovered partition is compared with the ground-truth architecture, the 100 runs of a method are tested against the single ground-truth value of the normalized TurboMQ using the one-sample Wilcoxon signed-rank test.

Statistical tests use a significance threshold of $\alpha = 0.05$. For the mapping comparisons, the resulting $p$-values are adjusted using Holm's procedure across the ten systems, separately for each metric and each pair of compared configurations.

A significant result indicates that the observed difference would be unlikely if the two methods or configurations produced equivalent results, but it does not indicate the magnitude of the difference. With 100 runs per configuration, even a small difference can reach statistical significance. Differences are therefore also quantified with Cliff's delta as an effect size~\cite{cliff}, classified as negligible ($|\delta| < 0.147$), small ($< 0.33$), medium ($< 0.474$), or large~\cite{romano2006}. Between two configurations, delta is computed on the two sets of 100 scores as independent groups, and the significance test is paired. Against the ground-truth value, which is a constant, delta is the proportion of runs above that value minus the proportion below it. A difference that is significant but negligible is reported but not interpreted as an improvement.

Results are reported per system rather than averaged across systems, since averaging can conceal effects that differ across systems with different graph properties. The definitions and interpretation of the recovery and mapping metrics are given in Section~\ref{sec:bg-eval}.

\section{Cross-Study Evaluation Design\label{sec:cross_study_eval}}
The five studies were conducted on separately scoped benchmarks and, in part, with different input features and pipelines, so their reported results cannot be compared directly. For this thesis, four evaluations were therefore conducted in addition to the published work, followed by a correlation analysis with system properties. Their results are reported together with those of the studies in Chapter~\ref{ch:findings}. Unless stated otherwise, the models, input features, training settings, and evaluation metrics are those described in Section~\ref{sec:learning_settings}.
 
The first two evaluations revisit recovery methods from Papers~I, II, and~IV on all systems in Table~\ref{table:dataset_details}. Both use Ward-linkage agglomerative clustering of the learned file embeddings, with the number of clusters set to the number of modules in the ground-truth architecture. Each method is run 100 times per system. Holding the clustering procedure fixed removes differences in clustering algorithms and cluster-count selection from the comparison.
 
The first evaluation compares the contrastive approach of Paper~I with the reconstruction-based approach of Paper~II using the GAT encoder. Paper~I is extended to use the input features of Paper~II while retaining its own training pipeline. The comparison therefore uses shared input features, although differences in training settings remain.
 
The second evaluation compares the attributed dependency graph of Paper~II, using GCN and GAT, with the structure-only file-level and folder-augmented representations of Paper~IV. It also compares the dependency cohesion of the recovered partitions with that of the ground-truth architectures.
 
The remaining two evaluations concern C2A mapping on the ten-system mapping benchmark. Within each comparison, the underlying file-level dependency graph, input features, 100 labeled sets per system, and training procedure are held fixed.
 
The third evaluation adds HGT to the comparison of Paper~III to examine its performance with typed dependencies. It uses that study's file-level graph and input features, with two message-passing layers and messages aggregated from source to target, matching the depth and direction of its main configuration.
 
The fourth evaluation examines whether the contribution of dependency types varies with the input representation. It compares typed GAT, with one channel per relation type, against merged GAT, which collapses all types into a single relation, using the four input representations from Paper~V: Word2Vec, Node2Vec, zero-shot UniXcoder, and fine-tuned UniXcoder. Both variants aggregate messages from source to target. None of these representations includes folder-path features, so this evaluation examines dependency types without organizational information in the node features.

\section{Synthesis of Research Findings \label{sec:contruibutions}}

This section combines the findings of the five studies with the cross-study results in Section~\ref{sec:cross_study_results} to answer the research questions. The synthesis follows the three research objectives, examining the use of representation learning for recovery and mapping, the information carried by individual implementation signals, and the contribution of additional graph structure.

% ===== OBJECTIVE 1 Answers START ===========
\subsection{Objective~1: Representation Learning for Recovery and Mapping\label{sec:cont_1}}

Objective~1 examines how graph-based representation learning supports architecture recovery and C2A mapping. The findings address the combination of implementation signals (RQ1.1), the treatment of dependency types (RQ1.2), and the effects of learning objective, encoder architecture, and depth (RQ1.3).

\paragraph{RQ1.1: Joint representation of implementation signals.} Papers~I--III combine dependencies, code identifiers, and folder organization to learn representations for recovery and mapping. These methods improve on their respective baselines in reference agreement for recovery and F1 for mapping. The results support the combined representations, but do not establish how much each signal contributes.

In Paper~III, an MLP using the same file features also outperforms the Naive Bayes baseline on every system under both F1 metrics. Improvement over that baseline therefore does not, by itself, demonstrate a benefit from dependency-based message passing.

\paragraph{RQ1.2: Modeling dependency types.} Papers~I--III represent dependency types as separate relations, each processed by its own encoder channel, and combine the outputs by summation. Paper~III compares this design with merging all dependencies into a single relation. With lexical and folder-token features, separate relations significantly improve both GCN and GAT across all evaluated systems. However, the separate channels also add parameters, so the comparison does not isolate dependency typing from model capacity. Papers I and II do not test a merged alternative.

The cross-study mapping comparison extends this evaluation to the folder-free representations of Paper~V. Separate relations generally benefit GAT, but the benefit is less consistent than in Paper~III and varies across representations and systems, with significant losses on some systems (Section~\ref{sec:mapping_cross_study}). HGT does not match GAT on the typed dependency graph, showing that the use of dependency types alone does not determine predictor performance.

Recovery provides less consistent support for separate relations. In Paper~IV, preliminary experiments on file-level dependency graphs showed markedly lower performance with separate relations, so the reported dependency-only comparisons use merged dependencies. With folder nodes and containment relations included, preserving dependency types gives modest benefits that vary across systems and evaluation measures.

Overall, separate dependency relations benefit mapping more consistently than recovery in the evaluated settings. Their effects vary with the input representations and encoder, but differences between the studies prevent these factors from being isolated.

\paragraph{RQ1.3: Learning objective, encoder architecture, and depth.} The studies examine how these three choices affect recovery and mapping.

\begin{itemize}[leftmargin=1.1em, topsep=3pt] % topsep=3pt, itemsep=1pt
\item \emph{Learning objective:} The cross-study evaluation in Section~\ref{sec:cont_recon} compares the contrastive approach of Paper~I with the reconstruction-based approach of Paper~II using common node features and a GAT encoder. Reconstruction generally achieves better agreement with the reference decomposition, although the advantage is not universal. Because the approaches retain different training settings, the comparison supports the reconstruction-based approach without isolating the learning objective alone.

\item \emph{Encoder architecture:} GAT generally outperforms GCN across recovery and mapping (Papers~II and~III), and HGT in the cross-study mapping comparison. GCN uses degree-normalized aggregation, whereas GAT learns weights for neighboring representations. However, the models also differ in parameterization, so these results cannot be attributed to attention alone. In mapping, GAT usually outperforms the MLP, while GCN frequently underperforms it. Access to dependencies therefore does not guarantee better predictions.

\item \emph{Encoder depth:} Paper~III finds no consistent benefit from increasing message-passing depth. A second layer improves performance on some systems and reduces it on others.
\end{itemize}

\begin{GrayBox}{Summary of Objective~1}
Combining dependency, lexical, and folder signals improves on the evaluated baselines in recovery and mapping, although the contribution of each signal is not isolated (RQ1.1). Preserving dependency types benefits mapping more consistently than recovery, with effects varying across inputs and encoders (RQ1.2). The reconstruction-based approach generally achieves better reference agreement than the contrastive approach, but their training settings also differ. GAT generally outperforms GCN across both tasks and HGT in the cross-study mapping comparison, while increasing encoder depth has no consistent benefit (RQ1.3).
\end{GrayBox}
% _________ Objective~2 __________________

\subsection{Objective~2: Architectural Information in Implementation Signals \label{sec:cont_2}}

Objective~2 (Section~\ref{sec:obj_2}) examines the architectural information carried by individual implementation signals. The findings address recovery from dependency structure alone (RQ2.1), dependency-guided adaptation of contextual code representations (RQ2.2), and the comparison of structural, lexical, and contextual file representations (RQ2.3).

\paragraph{RQ2.1: Recovery from dependency structure.} Paper~IV shows that dependency structure alone supports recovery. Node2Vec and GAT-DC outperform the classical recovery baselines, while plain GAT is generally weaker than both.

Structural reach helps explain this difference. Node2Vec and GAT-DC achieve better reference agreement than the two-layer GAT on most systems. Applying diffusion to the GAT input graph closes much of the gap to Node2Vec, suggesting that access to a wider dependency neighborhood contributes to recovery performance.

Performance also depends on how closely dependency structure follows the reference decomposition. Recovery is strongest when dependencies are concentrated within reference modules and remains difficult when within-module and cross-module dependencies are similarly dense, as on Hadoop and TeamMates.

The evaluation criterion matters as well (Section~\ref{sec:recovery_cross_study}). Node2Vec produces the most dependency-cohesive partitions, while GAT-DC improves reference agreement over plain GAT on most systems without a corresponding advantage in dependency cohesion.

\paragraph{RQ2.2: Dependency-guided adaptation of code representations.} Paper~V finds that dependency-guided fine-tuning of UniXcoder improves mapping performance over its zero-shot form on nearly all systems. Both representations are held fixed during classifier training and evaluated using the same MLP and labeled sets, without folder information or additional message passing.

Fine-tuning uses a contrastive objective with positive pairs drawn mainly from two-hop dependency neighborhoods. This choice follows the observation in Paper~IV that structural context beyond direct neighbors can support recovery. With the classifier and evaluation conditions held fixed, the gains support adapting the pretrained representation to the target system using dependency information.

However, the comparison does not isolate the contribution of dependency-based pair selection, since it includes no fine-tuning alternative using pairs selected without dependency information.

\paragraph{RQ2.3: Comparing file representations.} Paper~V compares structural, lexical, and contextual file representations using the same graph-free MLP and labeled sets, without folder information or additional message passing. Representations that encode dependency information generally perform better. Node2Vec captures dependencies through random walks, while fine-tuned UniXcoder incorporates them through dependency-guided adaptation. Both generally outperform Word2Vec and zero-shot UniXcoder, although there are exceptions, including JabRef, where Word2Vec is among the strongest. Word2Vec and zero-shot UniXcoder show no consistent ordering, with each significantly outperforming the other on several systems.

Neither Node2Vec nor fine-tuned UniXcoder is uniformly best. Node2Vec performs significantly better on six systems under both F1 metrics, while fine-tuned UniXcoder performs significantly better on three systems under both metrics and additionally on HDC under macro-F1.

Together with the improvement from zero-shot to fine-tuned UniXcoder (RQ2.2), these findings suggest that dependency information contributes to the stronger representations. However, the representations also differ in content and training procedure, so the contribution of dependency information alone cannot be isolated.

\begin{GrayBox}{Summary of Objective~2}
Dependency structure alone supports recovery, with performance depending on structural reach and how closely dependencies follow the reference modules. Reference agreement and dependency cohesion favor different methods (RQ2.1). Dependency-guided fine-tuning improves UniXcoder over its zero-shot form on nearly all systems, although the contribution of dependency-based pair selection is not isolated (RQ2.2). Node2Vec and fine-tuned UniXcoder generally outperform Word2Vec and zero-shot UniXcoder in mapping without folder information or additional message passing, but neither is uniformly best. Differences in content and training prevent the advantage from being attributed solely to dependency information (RQ2.3).
\end{GrayBox}

% % _________ Objective~3 __________________
\subsection{Objective~3: Interaction Between Input Signals and Graph Structure \label{sec:cont_3}}

Objective~3 (Section~\ref{sec:obj_3}) examines how graph structure contributes beyond the initial file representations. The findings address dependency-neighbor aggregation and its direction (RQ3.1), folder organization (RQ3.2), and the additional detail provided by member nodes and edge attributes (RQ3.3).

\paragraph{RQ3.1: Dependency neighbors and aggregation direction.} Paper~V examines the contribution of dependency neighbors by comparing HGT, GAT, and a neighbor MLP with and without neighbor aggregation, holding file representations fixed. The neighbor MLP appends the mean of neighboring files' vectors to each file's own vector. These comparisons assess neighbor access within each predictor, avoiding the change in predictor architecture involved in comparing a GNN with a graph-free MLP.

Dependency neighbors mostly improve mapping beyond the information already present in the file representations, but the gains vary across predictors and inputs. For GAT and the neighbor MLP, gains are larger for Word2Vec and zero-shot UniXcoder, which do not encode dependencies, than for Node2Vec. However, fine-tuned UniXcoder benefits more than Node2Vec. GAT is generally the strongest predictor, while HGT gains the least from neighbor access. With GAT, fine-tuned UniXcoder scores higher than Node2Vec in micro-F1 on seven of the ten systems with either aggregation direction, up from three without aggregation (RQ2.3), whereas in macro-F1 the count rises only from four to five.

Aggregation direction also affects performance. Source-to-target aggregation updates a file using information from files that depend on it, while undirected aggregation permits information to flow in both directions. In Paper~V, source-to-target aggregation lowered median macro-F1 with Node2Vec, which already encodes dependency context, whereas undirected aggregation improved it. The preferred direction varied across systems rather than across predictors or input representations. Systems that combine low homophily with high average degree favored source-to-target aggregation, while several sparser systems favored undirected aggregation. However, making the graph undirected also adds reverse edges, so the comparison does not separate direction from neighborhood size, and the ten systems do not separate connectivity from homophily.

Paper~III examines aggregation direction for GAT and GCN and finds source-to-target aggregation generally preferable for GAT. This preference agrees with Paper~V on some systems but differs on others. The studies also differ in dependency typing, node features, depth, and training, so neither the benefit of aggregation nor the preferred direction can be assumed to transfer across settings.

These comparisons isolate neighbor access in mapping. The dependency-only recovery methods have no corresponding condition without dependency context. Their results instead show how recovery varies with structural reach and how closely dependencies follow reference-module boundaries (RQ2.1).

\paragraph{RQ3.2: Folder organization.} The studies represent folder organization either through directory tokens in file features (Papers~I--III) or through folder nodes and containment relations (Papers~IV and~V). In recovery, methods that include organizational information achieve better agreement with the reference decomposition, particularly where dependencies provide weak evidence of module boundaries. Dependency-only methods instead produce more dependency-cohesive partitions (Section~\ref{sec:recovery_cross_study}).

In mapping, Paper~V finds that adding folder nodes produces the largest and most consistent gains across the evaluated additions to the graph, with Word2Vec benefiting most. Across these configurations, folder nodes use the same folder-token features. With fine-tuned UniXcoder, the folder-aware model approaches the mapping performance of a rule based on directory hierarchy and the initial labeled set on most systems, exceeding it only on Lucene.

The overall gains do not establish a consistent benefit for files that the directory-based rule assigns incorrectly. On these files, the folder-aware model is more accurate than the model without folder nodes on some systems, similar on others, and less accurate on others, and on most of the systems where the rule makes errors it still assigns most of them incorrectly. The analysis does not isolate files whose module differs from the majority module of their directory. Folder location is therefore informative for the reference mappings, while whether the model handles such files reliably remains untested. These mapping findings apply to HGT with source-to-target dependency aggregation and hold with one or two layers.

\paragraph{RQ3.3: Member nodes and edge attributes.} Neither member-level nodes nor edge-level interaction attributes consistently improve performance in the evaluated settings.

In Paper~V, adding member nodes to the file-only graph lowers the median F1 for all three representations evaluated with HGT. When folder nodes are also present, the effect of adding member nodes varies with the representation. These additions change both the graph structure and how features enter the model, so their effects cannot be attributed to structure alone.

Paper~I reports small gains from edge attributes on some systems. However, the cross-study evaluation finds no significant improvement over the same model without these attributes (Section~\ref{sec:recovery_cross_study}). Paper~I attributes the limited benefit on TeamMates to edge attributes amplifying noisy cross-module interactions, suggesting that additional interaction detail may be less useful where dependencies poorly reflect module boundaries.

\begin{GrayBox}{Summary of Objective~3}
Dependency-neighbor aggregation improves mapping beyond the initial file representations, most reliably for GAT and the neighbor MLP. The magnitude of improvement depends on both the predictor and the input representation, with fine-tuned UniXcoder gaining more than Node2Vec, while the preferred aggregation direction varies across systems (RQ3.1). Folder organization provides the strongest additional signal in the evaluated mapping configurations, but does not consistently help correct files misclassified by the directory-based rule. In recovery, higher agreement with the reference architecture can coincide with weaker dependency cohesion (RQ3.2). Adding finer-grained structure does not extend these benefits consistently. Member-level nodes give no consistent improvement in mapping, and edge-level attributes give no significant gain in the cross-study recovery evaluation (RQ3.3).
\end{GrayBox}

\chapter{Discussion \label{ch:discussion}}
 \chaptertoc

This chapter interprets the findings across the five studies and presents an exploratory analysis of how system properties relate to recovery performance. It examines differences between recovery-method rankings under reference agreement and dependency cohesion, the relationship between dependency homophily and recovery performance, and the role of structural reach in recovery and mapping. It concludes with the limitations of the work. Unless directly tested, the proposed explanations remain interpretations of the observed patterns.

\section{Interpretation of the Findings}

The findings raise three questions for interpretation: why evaluation criteria favor different methods, how system properties relate to recovery performance, and how the available dependency context affects recovery and mapping. The following subsections examine these questions across the studies.

\subsection{Reference Alignment and Dependency Cohesion}

In the cross-study recovery comparison (Section~\ref{sec:recovery_cross_study}), attributed GCN and GAT show the strongest agreement with the reference decomposition, whereas file-level structure-only methods produce more dependency-cohesive partitions. Node2Vec has the highest median normalized TurboMQ. Several factors may explain these different rankings.

TurboMQ rewards dependency concentration within clusters, while file-level structure-only methods learn exclusively from the dependency graph. Although their objectives do not explicitly optimize cohesion or coupling, learning from dependency proximity may favor partitions that score well on this measure.

Attributed representations also include folder paths and identifiers, which reflect how developers organize and describe responsibilities. These signals may support agreement with the reference decomposition without increasing dependency cohesion.

The reference decomposition itself need not maximize dependency modularity. Utility or cross-cutting code may receive dependencies from several modules, so matching its reference assignment need not produce the most dependency-cohesive partition.

The compared methods differ in graph construction, input information, and learning configuration. These explanations are therefore plausible interpretations of the observed rankings, but the comparisons do not isolate their individual contributions.
% -----------------------------------------
\subsection{System Properties and Recovery Performance}

We examine associations between recovery performance and benchmark-system properties. For each method in the cross-study recovery evaluation, we correlate per-system median scores with dependency homophily and average module size using Kendall's $\tau$ across the fourteen systems (Figure~\ref{fig:recovery-correlations}). Given the small sample and multiple tests, these correlations are treated as exploratory associations rather than independent effects.

\begin{figure}[!htb]
    \centering
    \includegraphics[width=0.98\textwidth]{figures/correlations_recovery.pdf}
    \caption[Correlation between architecture recovery metrics and system properties.]{\small Kendall's $\tau$ correlation between recovery outcomes (MoJoFM, ARI, \tmq{}) and two system properties, homophily $\mathcal{H}$ and average module size $\langle \mathcal{M}\rangle$, per method. GAT, GAT-DC, and N2V (structure-only) operate on the homogeneous dependency graph alone; GCN and GAT (attributed graph) operate on the multi-relational dependency graph with node features derived from file location and code identifiers. \label{fig:recovery-correlations}}
\end{figure}
Dependency homophily shows the clearest association with performance, particularly for structure-only methods. The structure-only GAT, GAT-DC, and Node2Vec all show significant positive associations with homophily for MoJoFM and \tmq{}, while only the GAT does so for ARI. The attributed GCN and GAT show weaker and less consistent associations. Lexical and file-location attributes may provide complementary evidence when dependencies cross module boundaries, but these comparisons do not isolate their contribution from other methodological differences.

The Node2Vec results are consistent with its reliance on dependency structure alone, so its sensitivity to homophily may be a property of the method and not only of the benchmark. Random walks define the contexts from which file representations are learned, without module labels to distinguish within-module from cross-module dependencies. When dependencies frequently cross module boundaries, files from different modules may therefore appear in similar walk contexts. The positive associations with MoJoFM and \tmq{} are consistent with this interpretation but do not establish the mechanism. Because homophily is computed from the reference decomposition, it provides a retrospective explanation and cannot guide the choice of a representation in advance.

Associations involving \tmq{} need a separate reading. Homophily describes dependency concentration within reference modules, whereas \tmq{} rewards dependency concentration within recovered clusters and is normalized by the number of clusters, so its associations with homophily and module size are partly built into the metric. They describe the structural quality that \tmq{} measures and do not independently support an effect on recovery accuracy.

Average module size is positively associated with MoJoFM for three of the five methods, but with ARI for none. This pattern is difficult to interpret independently of other system properties: OODT and Libxml have both the smallest modules and the lowest homophily, while larger modules tend to occur in larger systems. With fourteen systems, these associations cannot be separated, so no independent effect of module size is inferred.

\subsection{Structural Reach and Neighborhood Aggregation\label{sec:structural-reach}}
We use structural reach to describe the extent of the dependency neighborhood from which a file's representation can incorporate information through message passing, diffusion, or random walks. The studies vary these mechanisms rather than measuring reach directly.

In dependency-only recovery, Paper~IV finds that GAT-DC and Node2Vec outperform plain GAT overall. GAT-DC makes diffusion-close nodes directly accessible to the encoder, while Node2Vec learns from contexts formed by random walks. These results suggest that the two-hop neighborhood available to plain GAT provides insufficient context on some systems.

However, GAT-DC also uses system-specific settings for depth and the number of retained diffusion neighbors. Paper~IV examines sensitivity to the retained-neighbor count, but the comparison with plain GAT does not isolate the contribution of structural reach under matched settings.

Increasing depth offers another way to access more distant nodes, but it is not necessarily equivalent to diffusion or random walks. Additional layers repeatedly aggregate information over the same graph, diffusion changes which nodes are directly connected, and random walks define the contexts used to learn representations. Paper~III finds mixed effects from adding layers in mapping, with neither connectivity nor homophily alone explaining when greater depth helps. These mechanisms were not compared under matched conditions across tasks.

Where dependencies cross module boundaries, additional layers may mix information from different modules. Repeated aggregation may also make node representations less distinguishable through over-smoothing~\cite{gnn_oversmoothing}. Neither mechanism was measured directly in these studies, so both remain possible explanations for the mixed effects of depth.

In mapping, Paper~V shows that encoding dependency context in the input representation does not remove the potential benefit of neighbor aggregation during prediction. With file vectors held fixed, adding neighborhood aggregation produces different gains across predictors and directions, including when the input vectors already encode dependencies through Node2Vec. The usefulness of additional context therefore depends on how it is combined with the existing representation.

Aggregation direction also varies in usefulness across settings. Papers~III and~V favor different directions on several systems, but also differ in dependency typing, features, depth, and training. These differences were not individually tested as explanations. Moreover, undirected aggregation adds reverse edges, so its comparison with source-to-target aggregation does not separate direction from neighborhood size.

Taken together, the studies suggest that both the available dependency context and the mechanism used to incorporate it matter. Wider reach can support recovery and mapping, but its benefit depends on the initial representation, the predictor, and how closely dependencies follow module boundaries.

\section{Limitations \label{sec:limitations}}

The conclusions are limited by the systems, architectural representations, and methodological choices examined. Some limitations apply across all five studies, while others concern particular graph constructions, model configurations, or evaluation protocols.

\paragraph{Benchmark scope and external validity.}
The studies evaluate overlapping subsets of open-source Java, C, and C++ systems with published reference decompositions. The findings may not generalize to other programming languages, application domains, build environments, or architectural styles. Although the methods may be applied without a reference decomposition, agreement with an intended architecture cannot be assessed without a comparable reference. Chromium is the only large-scale system evaluated, so evidence of scalability is limited to a single system. Each system is evaluated at a particular version; the studies therefore do not establish robustness to refactoring or changes in dependency structure across releases.

The exploratory analysis across fourteen systems does not establish whether dependency homophily affects recovery independently of system size, module granularity, or other system properties.

\paragraph{Static dependencies.}
Static dependencies are extracted automatically with the Depends~\cite{depends} tool. The resulting graphs may omit runtime dependencies or dependencies the tool cannot resolve, and may include edges not realized at runtime. Recovery and mapping results therefore depend on the extracted graph's accuracy and coverage. Within this thesis, this limitation may affect dependency-derived signals, including dependency-guided fine-tuning of contextual embeddings. Folder and containment relations, lexical embeddings, and zero-shot contextual embeddings do not depend on this extraction. The studies neither independently validate extraction accuracy nor assess sensitivity to extraction errors.

\paragraph{Reference architectures and architectural representation.}
The reference decompositions were produced by system experts, industry partners, or researchers reconstructing architecture from documentation, and only one reference is available per system. They are not uniquely determined ground truths: reasonable disagreement may arise when module boundaries are unclear, files implement several concerns, or the intended architecture differs from the implementation. Source revisions and reference mappings are not always aligned, and build configuration determines which files are analyzed, so assignments may be outdated or missing. In the mapping studies, labels are sampled from the same reference used for evaluation, so an incorrect assignment can misdirect training and penalize a plausible prediction.

Reference granularity is a modeling choice: the same system can be represented by a few large modules or by more, smaller submodules. JabRef, for example, has six modules of very uneven size, whereas TeamMates has 15 that could plausibly be grouped into fewer, higher-level modules. Merging modules keeps existing internal dependencies within modules and may make dependencies between modules internal as well, so homophily can only increase or stay unchanged; splitting has the opposite effect. Even with the same dependency graph, the chosen granularity can therefore change homophily, the reference partition's TurboMQ, and potentially the recovery and mapping scores.

More generally, both tasks represent architecture as a flat, exclusive partition of files into modules. Files implementing multiple concerns must be assigned to a single module; overlapping responsibilities, cross-cutting infrastructure, and hierarchical decompositions are not evaluated. The reported scores therefore measure agreement with one file-level architectural view, not whether the recovered or predicted architecture fully represents the system.

\paragraph{Mapping protocol.} The random labeled sample comprises 5\% of files, bounded between 30 and 200, with five systems at the 30-file minimum, so label count and proportion vary with system size and were not varied independently. The mapping models are also transductive, since all system files are available during training.

\paragraph{Organizational signals and shared provenance.} Folder organization is the strongest additional signal identified under Objective~3, but it introduces a validity concern. Folder hierarchies and reference decompositions may reflect shared design decisions: developers may organize folders around intended module boundaries, and researchers may use folder structure when constructing reference decompositions. A directory-based baseline in the mapping study agrees closely with the reference mappings, but the extent of this overlap was not otherwise quantified. Folder paths also inform file-node features in Papers~I--III and initialize folder nodes in Paper~V. The gains from folder information may therefore partly reflect shared provenance between inputs and reference labels rather than independent architectural evidence. Systems with reorganized, flattened, or architecture-inconsistent directory structures were not evaluated.

\paragraph{Representation, objective, and comparison choices.} The studies use graph abstractions that encode different notions of structural relevance. Several models use binary file-level adjacency, which omits dependency frequency. Paper~I includes member-level interaction counts and types as edge attributes, whereas Paper~IV uses PPR weights to represent topology-derived proximity. These represent different notions of edge strength and were not compared across encoders and tasks. Aggregation direction was varied only in mapping, so its effect on recovery remains untested. Member-level information was evaluated only as an aggregate node per file and with one encoder, HGT, so the results do not show that it is uninformative under other designs or encoders.

Recovery objectives optimize proxies rather than agreement with the intended architecture, and results also depend on the clustering method and, in the recovery studies, on the number of clusters, which was searched over a range. The cross-study evaluations fix the cluster count to the reference count, which improves comparability but supplies information generally unavailable in practice.

Between-method comparisons involve differences in graph construction, inputs, training, depth, and parameter count, which limit attribution of performance differences to individual choices. Hyperparameter selection on the evaluation systems using reference-based metrics may also favor more extensively tuned methods.

\paragraph{Stochasticity and reproducibility.} Results are summarized by medians over 100 runs per configuration in all five studies. Input representations were computed once and reused, except for Node2Vec in recovery, which was recomputed for each run. Reported variation therefore excludes the stochasticity of the fixed representations. With 100 runs, even small differences can reach statistical significance without being practically meaningful. Effect sizes are therefore reported alongside $p$-values, and interpretation should consider effect magnitude rather than significance alone.

In the mapping studies, each run pairs a labeled set with a training seed, so their contributions to variation are not separated in the main evaluation. When Paper~III varied the training seed with the labeled set held fixed, the ranking of a few configurations changed across seeds, whereas some advantages were robust. These results indicate seed sensitivity, but the limited comparisons do not characterize it fully. Close rankings should therefore be interpreted cautiously.

\chapter[Conclusion]{Conclusion and Future Work \label{ch:conclusion}}
\chaptertoc

This chapter concludes the thesis by bringing together the findings on graph-based representation learning for software architecture recovery and C2A mapping. It summarizes the conclusions across the three research objectives, then outlines directions for further research arising from the findings and limitations of the work.

\section{Conclusion \label{sec:conclusion}}

This thesis examined how graph-based representation learning can support software architecture recovery and C2A mapping, and what different implementation signals contribute to these tasks. Recovery was studied as an unsupervised task and mapping as a supervised task with limited labeled data. Across five studies, the work progressed from learning joint representations of static dependencies, folder organization, and source-code content to examining their individual contributions and their interactions with graph structure.

The first objective examined whether dependency, lexical, and organizational signals could be combined in learned representations for recovery and mapping, and how performance depended on the learning objective and model configuration. The joint representations supported both tasks, although the evidence differed between them. In recovery, the approaches of Papers~I and~II improved on or matched the evaluated baselines across most comparisons. In mapping, however, improvement over the Naive Bayes baseline was not specific to the GNN models. Both the GNN models of Paper~III and an MLP using the same features outperformed that baseline. This improvement therefore does not by itself establish a benefit from message passing.

In the recovery comparison using a common GAT encoder and input features, the reconstruction-based approach generally produced better agreement with the reference decompositions than the contrastive approach. The approaches retained different training settings, so the comparison does not isolate the learning objective alone. Encoder choice also mattered: GAT generally outperformed GCN in both tasks. Modeling dependency relations separately improved mapping with lexical and folder-token features (Paper~III), although the encoder also had more parameters. With file vectors without folder-path features, the benefit was smaller and varied across representations and systems, as shown in the cross-study mapping evaluation. Separate relations gave no benefit in preliminary tests in dependency-only recovery (Paper~IV). Relation-specific modeling was therefore useful under some input representations and tasks, rather than consistently beneficial.

The joint-signal comparisons did not separate the contributions of the individual signals. The second objective therefore examined what architectural information static dependencies and source-code content carry, and how representation choices make that information available. In recovery from static dependencies alone, the results suggest that the extent of dependency context encoded in a file's representation (structural reach) matters. Node2Vec extends this reach through random walks and GAT-DC through PPR diffusion. Both outperformed the classical baselines on most systems, whereas the two-layer GAT, limited to its two-hop neighborhood, was generally weaker. Agreement with the reference decomposition was lower where within-module and cross-module dependencies were similarly dense, whereas the dependency cohesion of the recovered partitions frequently matched or exceeded that of the reference. Dependency structure alone therefore supported recovery to a bounded extent: its usefulness depended on structural reach, on how well the reference modules were separated by dependencies, and on the evaluation criterion.

In mapping with an MLP, Word2Vec and zero-shot UniXcoder showed no consistent ordering, so the pretrained code transformer was not consistently better than a lexical representation. Dependency-guided fine-tuning improved UniXcoder on nearly all systems, supporting adaptation of the pretrained representation to the target system using dependency information. Node2Vec and fine-tuned UniXcoder generally outperformed the other two representations. Neither of the two was uniformly best: Node2Vec most often performed best, while fine-tuned UniXcoder was significantly stronger on some systems. Dependency information was therefore useful in mapping as in recovery, regardless of representation family, although differences in content and training prevent attributing the performance differences to dependency information alone.

The information carried by individual file representations did not establish what additional graph context could contribute. The third objective therefore examined how dependency-based message passing, folder organization, and member-level detail changed their usefulness. With undirected aggregation and fixed file representations, GAT and an MLP supplied with mean neighbor vectors improved on most systems for every representation, with no significant losses. Gains were largest for zero-shot UniXcoder and smallest for Node2Vec. Fine-tuned UniXcoder gained more than Node2Vec and had the highest median macro-F1 across systems for every predictor. The benefit of aggregation therefore depended on how dependency context was already encoded.

Aggregation direction also mattered. Source-to-target aggregation lowered median macro-F1 with Node2Vec, and the preferred direction depended on the system rather than the predictor or representation. Papers~III and~V agreed on some systems but differed on others, so neither the benefit nor the preferred direction can be assumed to transfer across setups. Undirected aggregation also added reverse edges, so direction and neighborhood size were not separated.

Folder organization supplied architectural evidence beyond static dependencies alone. Across the recovery studies, methods using organizational information agreed more closely with the reference decomposition, particularly in Paper~IV where dependencies gave limited evidence of module boundaries, but produced less dependency-cohesive partitions than file-level dependency-only methods. Reference agreement and dependency cohesion therefore favored different configurations. In mapping with HGT and source-to-target dependency aggregation, folder nodes improved every file representation, but the model with fine-tuned UniXcoder did not consistently outperform the directory-based baseline, limiting the evidence for a benefit beyond directory organization itself (Paper~V). Folder information and the reference decomposition may also overlap because directories are consulted during reference construction; the extent of this overlap was not quantified.

Member-level detail gave no consistent improvement in the evaluated configurations. With HGT and source-to-target dependency aggregation, member nodes lowered median mapping F1 for all three representations without folders and had representation-dependent effects with folders (Paper~V). Since member nodes also changed how features entered the model, their effects cannot be attributed to the added structure alone. In the cross-study recovery evaluation, member-level edge attributes gave no significant improvement over the same model without these attributes. These findings therefore concern the evaluated encoders and representations, not the usefulness of member-level information in general.

Taken together, dependency information remained useful, but encoding it in file representations did not make message passing redundant, and folder organization supplied further information. The dependence on encoder choice observed under Objective~1 recurred as a dependence on predictor and aggregation direction, and across the studies no representation or configuration was uniformly preferable: the contribution of each signal depended on how it was represented and combined with other evidence.

\section{Future Work~\label{sec:future_work}}
A first direction is to determine which aspects of graph context account for the observed performance differences. Undirected aggregation changed both propagation direction and neighborhood size, while member nodes changed graph structure and feature placement. Comparing incoming, outgoing, and combined neighborhoods at matched sizes could help distinguish direction from neighborhood size, while member-level comparisons should preserve feature content. Parameter-matched comparisons of relation-specific and collapsed-relation models could distinguish relational detail from model capacity.
 
Paper~I included interaction frequency and type together as member-level edge attributes. The cross-study recovery evaluation found no significant improvement from these attributes, but did not isolate the contribution of frequency. Whether frequency adds architectural information, and how it should enter representation learning through edge weights, attention terms, or relation encodings, remains open for both recovery and mapping.
 
A second direction concerns configuration selection and evaluation on unfamiliar and evolving systems. The benefit and preferred direction of neighbor aggregation varied across systems, but dependency homophily, used to interpret these differences, requires reference module assignments. Future work should examine whether properties observable in the dependency graph alone can guide configuration selection, with selection rules evaluated on systems not used to develop them. Folder-aware methods could also be assessed across systems that differ in how closely directories match the reference modules. Reporting performance separately for files whose module differs from that of their directory would help establish whether the methods provide useful predictions beyond directory organization.
 
The mapping evaluations made all system files available, leaving performance on subsequently introduced files untested. Future work could evaluate whether a model trained on mapped files from one version can assign new and changed files in later versions without retraining. The version history could also supply evolutionary signals, such as files that change together, which may carry architectural information that dependencies, folders, and code content do not. Practitioner studies could then assess whether the predictions support architecture maintenance.
